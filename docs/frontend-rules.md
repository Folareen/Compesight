# Frontend Rules

Next.js dashboard in [`frontend/`](../frontend/). Read [rules.md](rules.md) first — the universal rules apply here too.

## Read this before using any framework API

**This is Next.js 16 and React 19 — newer than most training data.** Writing from memory will produce code that looks right and is wrong. The bundled docs are in `frontend/node_modules/next/dist/docs/` (resolve from the `frontend/` directory, not the repo root) — check them before reaching for a framework API.

Changes that will bite:

- **Middleware is now called Proxy.** `proxy.ts` at the project root, not `middleware.ts`. Export as default or as a named `proxy` export.
- **`cookies()` and `headers()` are async.** `await cookies()`.
- **`fetch` is *not* cached by default.** It blocks render until complete. Opt in with the `use cache` directive, or wrap the fetching component in `<Suspense>` to stream.
- **Proxy is explicitly not a session-management or authorization layer.** The Next docs say so directly. Use it for optimistic redirects only; every real authorization check happens server-side at the point of data access.

The `<!-- BEGIN:nextjs-agent-rules -->` block in [`AGENTS.md`](../frontend/AGENTS.md) is generated by `next dev` and says the same thing. Commit it with your work — deleting it just re-creates an uncommitted change.

## TypeScript

- **Strict, no `any`.** Use `unknown` and narrow it.
- **Path alias `@/*`** is configured — use it instead of `../../..`.
- Type API responses explicitly. `snake_case` keys, matching the backend — the frontend does not transform them ([api-conventions.md](api-conventions.md)).

## Components

- **Server Components by default.** Add `"use client"` only for real interactivity — state, effects, event handlers — and push it as far down the tree as possible. A client boundary high in the tree drags everything below it into the bundle.
- **No business logic here.** Classification, diffing, urgency assignment, battlecard maintenance all live in the backend. The dashboard renders what the API returns. If a calculation feels like product logic, it belongs in a service in `backend/app/services/`.
- Reusable components in `components/`. Build the specs in [design-system.md](design-system.md) as real components — `UrgencyBadge`, `HealthPill`, `FindingCard`, `DiffView`, `BattlecardPanel`, `EmptyState` — and reuse them rather than re-implementing per screen.

## Data

- **Fetch server-side in Server Components**, with the session token. Never call FastAPI directly from a Client Component with a token in the browser.
- Mutations go through Server Actions or route handlers that forward to FastAPI.
- Wrap slow reads in `<Suspense>`. Since `fetch` blocks render by default, an unwrapped slow call holds the whole route.
- Cursor pagination on all lists — findings grow without bound ([api-conventions.md](api-conventions.md)).

## Auth

Clerk owns identity; the backend owns authorization.

- Proxy does optimistic redirects only.
- **Never render data the backend hasn't authorized.** Don't fetch broadly and filter client-side — the filtering is the security boundary, and it's in the wrong process.
- A workspace switcher changes session context; it never sends a `workspace_id` to the API.

## Code simplicity

Same governing rule as the backend:

> **Validate untrusted data once at the boundary. Trust typed application code everywhere else.**

On the frontend there is exactly one untrusted boundary worth defending: **the API response**. Type it once where it arrives, and everything downstream — components, props, helpers — works with real types and no runtime ceremony.

### Don't propagate `unknown`

Be suspicious of `unknown`, `Record<string, unknown>`, and `any` in component code. An API response has a known shape; declare it as a type where the fetch happens, with literal unions for the closed sets (`urgency`, `change_type`, health status).

The pattern to avoid is an `asFinding(value: unknown)` helper that checks the value is a non-null object and then casts anyway — that is not validation, and it spreads the broad type further instead of fixing it. Fix the type at the fetch site and the helper disappears.

### Prefer discriminated unions

Where states are mutually exclusive, model them so impossible states can't be represented. A discriminated union, never a bag of optional booleans that permits nonsense combinations.

This applies directly to the components in [design-system.md](design-system.md): a `FindingCard` is either baseline or a change carrying an urgency, never both and never neither. The four source-health states and the three `EmptyState` cases are the same shape. Conflating "nothing changed" with "can't check" is a product bug ([rules.md](rules.md)) — a union makes it a compile error instead of something code review has to catch.

### No fake validation, no defensive coercion

- Don't write `typeof x === "object" && x !== null && "id" in x` and then cast anyway. Either trust the typed boundary or validate it properly there.
- Don't coerce values the type already guarantees: no `String(finding.id)` when `id: string`, no `!!value`, no `` `${value}` ``.
- Don't chain `data?.competitor?.battlecard?.pricing?.tiers` when the type says those exist. Optional chaining should reflect real optionality — a nullable field, a not-yet-loaded resource — not uncertainty about the codebase.
- Don't default to `?? ""` or `?? []` where absence means something. An empty findings array because the request failed must not render as "nothing changed".

### Avoid helper and abstraction noise

- No one-caller, one-line helpers that only read a field or call `.trim()`. Inline them.
- No generic converters: `toString`, `safeString`, `normalizeValue`, `asRecord`, `getString(obj, key)`.
- No near-identical duplicate types (`Finding` / `FindingData` / `FindingDTO` / `FindingResponse`) unless the contracts genuinely differ. We consume `snake_case` JSON directly ([api-conventions.md](api-conventions.md)) — there is no mapping layer, so don't build one.
- No interfaces or wrappers created purely because a component or module exists.
- Don't over-abstract two similar-looking components into one generic one with eight props. Obvious duplication beats a bad abstraction.

### Keep it readable

- **Early returns** over nested conditionals.
- **No nested ternaries.** A status with four states is a `switch` or a lookup object, not a ternary chain.
- **No useless intermediates** — three consts to reach one derived value.
- **Comments explain why.** Delete `// map over findings`. Keep the note about why a value gets re-fetched after a mutation.
- **`unknown` over `any`** when something genuinely is unknown, then narrow it once.

### What to preserve

Real uncertainty still needs handling:

failed or in-flight API requests · genuinely nullable fields (`muted_until`, `last_success_at`, a competitor with no battlecard yet) · empty lists that are legitimately empty · loading and error states · form input before validation · anything a user typed

> Defend against external uncertainty, not against your own typed code.

## Styling

- **Tailwind v4**, configured in CSS at [`app/globals.css`](../frontend/app/globals.css). There is no `tailwind.config.js` — don't create one.
- **Never write a raw hex value in a component.** Use the tokens in [design-system.md](design-system.md). Missing colour → add a token.
- Both themes, always. Dark is not an afterthought; dashboards get left open.
- Colour is never the sole carrier of meaning — urgency and health always carry a label too.

## Secrets

**Never put a secret in a `NEXT_PUBLIC_` variable.** That prefix means "shipped to the browser". Server-only env vars stay unprefixed and are read in Server Components, Server Actions, or route handlers.

## Tests

`npm run lint` must pass. Component tests for genuinely stateful pieces (routing rule editor, feedback buttons); one end-to-end path — sign in, add competitor, see baseline — is worth more than broad shallow coverage. Full policy in [rules.md](rules.md#testing).
